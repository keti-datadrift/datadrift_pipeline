# 실행 및 운영

## 구성

- UI: Next.js, `http://121.126.210.3:18091/ko/workspaces`
- API: FastAPI, loopback `127.0.0.1:18092` (UI의 `/api/*`로 프록시)
- API 문서: 서버에서 `http://127.0.0.1:18092/api/docs`
- 저장소: `.runtime/catalog.sqlite`, SQLite WAL; 단일 호스트/단일 워커 구성
- GPU 0: 학습·평가, 기존 전용 Python 환경 `/data/hslim/venvs/gemma4-12b-transformers-dev/bin/python`
- GPU 1: 접수 상태에 따라 기동·종료하는 모델 API용 vLLM 2B·4B 서버. 기존 다른 프로젝트의 vLLM 프로세스는 유지합니다.
- 기본 모델: `/data/hslim/models/Qwen3.5-2B`, `/data/hslim/models/Qwen3.5-4B`
- 삭제 항목: SQLite `deleted_objects` / `deletion_batches`에 보관하며 [운영 복원 API](data-deletion.md)합니다. 원본 파일은 삭제하지 않으므로 삭제로 디스크 공간이 확보되지는 않습니다.
- 업로드한 이미지: `.runtime/uploads/<asset-id>/` (파일 원본), 레이블/이미지 경로/모델 출처는 SQLite에 저장
- 모델·로그·입력 스냅샷: `.runtime/jobs/<job-id>/`
- 로그인 없음. 기존 내부망 접근 범위에서 운영하며 방화벽이나 외부 공개 설정은 변경하지 않습니다.

## 설치

```sh
npm ci
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock.txt
DATADRIFT_INPUT_ROOT=/home/hslim/Code/datadrift .venv/bin/python -m backend.catalog
npm run build
mkdir -p .next/standalone/.next
cp -R .next/static .next/standalone/.next/
```

GPU 환경은 별도입니다. 현재 검증 환경은 torch 2.10.0+cu128,
transformers 5.18.0.dev0, peft 0.20.0이며 Qwen3_5ForConditionalGeneration을 지원해야 합니다.
기존 GPU 환경을 변경하지 않습니다. 모델은 로컬 파일만 읽습니다.
서비스 파일의 작업 경로·실행 파일·포트·환경변수를 환경에 맞춰 확인한 뒤 설치합니다.

```sh
cp deploy/datadrift-pipeline-*.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now datadrift-pipeline-api datadrift-pipeline-worker datadrift-pipeline-web datadrift-pipeline-vllm-runtime
```

`DATADRIFT_STATE`, `DATADRIFT_INPUT_ROOT`, `DATADRIFT_MODELS`,
`DATADRIFT_TRAIN_PYTHON`, `DATADRIFT_GPU`, `DATADRIFT_PUBLIC_ORIGIN`으로 경로와 실행 환경을 지정합니다.
프록시를 통한 브라우저 쓰기 요청은 `DATADRIFT_PUBLIC_ORIGIN`과 일치해야 합니다.
CLI 요청은 Origin 없이 내부 API에 접근합니다.

## 서비스 유지·관찰

```sh
systemctl --user status datadrift-pipeline-api datadrift-pipeline-worker datadrift-pipeline-web
journalctl --user -u datadrift-pipeline-api -u datadrift-pipeline-worker -u datadrift-pipeline-web -f
systemctl --user restart datadrift-pipeline-web
curl -f http://121.126.210.3:18091/api/health
loginctl show-user "$USER" -p Linger
```

API/UI 재시작은 실행 중인 워커 학습을 끊지 않습니다. 워커 재시작은 실행 중 작업과
해당 자식 프로세스를 종료합니다. 재시작 시 그 작업은 실패로 표시되며, 부분 산출물을
보존합니다. 사용자가 새 작업을 등록해야 합니다. 실행 중 모델 학습의 자동 이어하기는 제공하지 않습니다.
서비스의 Restart=always와 사용자 linger로 로그인 세션과 독립적으로 실행합니다.

## 데이터와 평가 해석

무신사 1,000개는 Codex의 시각 검토 레이블, GS SHOP 651개는 Gemma4의 의사 레이블입니다.
둘 다 사람 검증 정답이 아닙니다. 원본 SHA256, 출처, 기존 train/validation/test 분할,
평가 제외 속성을 보존합니다. 원본 이미지와 레이블 파일을 Git에 올리지 않습니다.
무신사 700/100/200, GS SHOP 490/81/80 분할을 사용합니다.
가져오기는 전체 검증 후 원자적으로 저장하며 동일 내용의 재실행은 중복 생성하지 않습니다.

재구성은 학습 및 미지정 데이터를 후보로 사용하고 선택 결과를 새 학습용 데이터로 저장합니다.
원본 분할은 보존하며 검증·테스트는 선별에서 제외합니다. 기본 선별 방식은 균형 혼합이고,
전체 합치기·무작위·출처 균형·기준 분포 맞추기도 지원합니다.
레이블 내보내기는 이미지 경로를 제외한 JSONL이며 이미지 파일 자체는 원본 저장소에 남습니다.

학습은 배치 1, SFT+LoRA rank/alpha 8, BF16, 언어 attention 레이어만 갱신합니다.
unknown과 평가 제외 속성 값은 손실에서 마스킹합니다. 학습 스텝 수는 전체 에포크 수와 다릅니다.
성공한 학습은 레지스트리에 새 어댑터 모델로 등록됩니다.
평가는 검증/테스트 분할에서 생성한 JSON과 AI 레이블의 일치도를 측정하며 파싱 실패도 오답으로 계산합니다.
평가 엔진은 Transformers+PEFT이며 기본 8장 배치입니다. `DATADRIFT_EVAL_BATCH_SIZE`로
1~32를 지정할 수 있습니다. 마지막 남은 이미지도 처리하며 CUDA OOM이면 미완료 배치만
절반으로 줄여 재시도합니다. 단일 이미지도 메모리 부족이면 실패를 보고합니다.
진행 화면은 입력 준비·모델 로딩·학습 가중치 적용·평가·결과 정리 단계, 배치 크기와 경과 시간을 표시합니다.
화면은 테스트 분할 전체 평가가 기본이며 검증을 선택하면 해당 검증 분할 전체를 평가합니다.
최대 샘플 수 입력은 제공하지 않습니다. API의 `sample_limit` 생략 또는 null도 전체 평가이고,
기존 자동화가 명시한 양수 제한은 유지합니다. 학습·평가의 모델 선택은 검색과 스크롤을 지원하며
긴 모델 이름은 펼친 목록에서 줄바꿈하여 표시합니다.
현재 속성 사전이 기본값입니다. 화면에서 `기존 속성 기준`이나 `비케이브 기준`으로
구분하지 않으며, 구형 학습 모델은 모델 목록·상세·실행 대상에서 제외합니다.
평가는 선택한 현재 데이터의 테스트 또는 검증 분할만 사용합니다.
모델의 학습 데이터를 다시 선택하도록 요구하지 않습니다. 평가 분할이 비어 있으면
실행 버튼과 제출 검사를 통해 접수를 막습니다.
목록 안쪽은 마우스로 잡아 위아래로 끌 수 있으며, 드래그를 마쳐도 모델을 선택하지 않습니다.
오른쪽 스크롤바, 휠, 터치 스크롤과 클릭·키보드 선택도 지원합니다.

## 모델 API의 vLLM 시작·종료

`datadrift-pipeline-vllm-2b`는 loopback `127.0.0.1:18093`,
`datadrift-pipeline-vllm-4b`는 `127.0.0.1:18094`에서 실행합니다.
두 서비스 모두 GPU 1, BF16, 최대 동시 8개, 컨텍스트 8192, GPU LoRA 2개,
CPU LoRA 64개 설정을 사용합니다. 이미지 입력은 기존과 같이 최대 512px로 전처리합니다.
`gpu-memory-utilization`은 2B `0.141`, 4B `0.291`입니다.
메모리 한도를 낮추려고 동시 처리 수·컨텍스트·캐시 관련 옵션을 줄이지 않았습니다.
현재 환경의 기동 프로파일은 8192 토큰 최대 동시 요청에 2B 8.00x·4B 8.11x 캐시 용량을 보고했고,
각 가족의 기본 모델·LoRA 3개 전환과 실제 이미지 요청 8개 동시 응답을 확인했습니다.
이 값은 현재 모델·GPU·입력 설정에서 확인한 값이며 다른 모델이나 GPU에서는 다시 확인해야 합니다.

API 워커는 `DATADRIFT_INFERENCE_BACKEND=vllm`과 `DATADRIFT_VLLM_2B_URL`,
`DATADRIFT_VLLM_4B_URL`로 연결합니다. 기존 영속 큐·비동기 202 응답·결과 조회는 유지하며,
선택한 모델과 LoRA를 요청마다 지정합니다. 기본 모델을 이미지마다 다시 로딩하지 않습니다.
서버 기동 중에는 최대 600초 준비를 기다리고, 서버 오류를 다른 엔진으로 조용히 우회하지 않습니다.
학습·평가는 이 설정의 영향을 받지 않고 GPU 0에서 Transformers+PEFT를 사용합니다.

```sh
# API·워커에도 DATADRIFT_VLLM_MANAGED=1을 설정합니다.
# 엔진을 별도로 부팅하지 않고 실행 관리자가 저장된 접수 상태를 복구합니다.
systemctl --user disable datadrift-pipeline-vllm-2b datadrift-pipeline-vllm-4b
systemctl --user enable --now datadrift-pipeline-vllm-runtime
systemctl --user status datadrift-pipeline-vllm-2b datadrift-pipeline-vllm-4b
journalctl --user -u datadrift-pipeline-vllm-2b -u datadrift-pipeline-vllm-4b -f
systemctl --user status datadrift-pipeline-vllm-runtime
journalctl --user -u datadrift-pipeline-vllm-runtime -n 100
systemctl --user restart datadrift-pipeline-vllm-runtime
# 엔진은 화면의 접수 중지·시작으로 조작합니다. 수동 stop은 접수 중이면 다시 기동됩니다.
curl -f http://127.0.0.1:18093/health
curl -f http://127.0.0.1:18094/health
```

`datadrift-pipeline-vllm-runtime`은 `Restart=always`·부팅 자동 시작·사용자 linger로 상시 실행합니다. 1초 간격으로 SQLite의 접수 상태와 대기/실행 중인 API 요청을 확인해 이 프로젝트의 두 엔진 유닛만 제어합니다. `접수 중지`는 새 요청을 409로 차단하며 이미 받은 요청은 모두 처리한 뒤 종료합니다. 같은 기본 모델의 다른 API가 접수 중이면 서버를 유지합니다. 완료·실패·취소된 요청은 서버를 붙잡지 않습니다. 학습·평가 작업은 엔진 기동 조건에 포함하지 않습니다.

두 엔진의 부팅 자동 시작은 비활성화합니다. 접수 설정은 SQLite에 보존하고 실행 관리자가 필요한 엔진만 복구합니다. 엔진의 `Restart=always`는 접수 중 발생한 장애를 복구하며, 관리자의 명시적 stop 뒤에는 재시작하지 않습니다. 시작을 요청한 뒤 HTTP 준비까지 기다려 화면에 모델 로딩 상태를 표시합니다. 종료 도중 다시 접수를 시작한 요청은 이전 프로세스에 보내지 않고 새 서버가 준비될 때까지 기다립니다. 관리자의 시작 명령 실패는 화면에 표시하고 30초 간격으로 재시도합니다. 기동 후 엔진 장애는 엔진 서비스의 10초 재시작 설정을 따릅니다. 관리자의 상태가 15초 이상 갱신되지 않으면 실행 상태 확인 경고를 표시하고 새 추론 실행을 보류합니다.

같은 GPU의 동시 기동이 vLLM 메모리 프로파일에 영향을 주므로 한 엔진의 HTTP 준비가 끝난 뒤 다음 엔진을 기동합니다. 다른 엔진이 로딩 중이면 GPU 메모리를 반환하는 종료도 잠시 기다립니다. 동시 처리·캐시·메모리 비율 설정은 위와 같습니다. 재부팅은 실제 시험하지 않았습니다.
실측 비교와 측정 조건은 [평가 엔진 비교](inference-engines.md)에 있습니다.

## 기본 속성과 데이터 전환

구형 카탈로그의 명시적 전환에는 `.venv/bin/python -m backend.standardize_catalog --apply`를
사용합니다. 대기·실행 중인 작업이 있으면 중단하며, 변경 전 SQLite 온라인 백업을
`.runtime/backups/before-standardize-*.sqlite`에 남깁니다. 현재 이미지·분할을 유지하고
기존 최신 속성 레이블을 사용하되 이후 수동 수정은 이력을 보존해 보수적으로 변환합니다.
새 속성을 검토하지 않은 수동 검토 완료 표시는 재검토 대기로 바뀝니다.
구형 모델에는 `retired_at`을 기록합니다. 원본 데이터·완료 작업과 모델 파일은 보존하며,
이전 카탈로그의 복구는 백업과 함께 기존 데이터 복구 절차를 따릅니다.
2스텝/소수 샘플 검증은 작동 확인이며 모델 품질 검증이나 전체 학습을 의미하지 않습니다.

새 드리프트 분석은 속성·카테고리의 JS 변화량과 통계 검정, 고정 이미지 임베딩 MMD를 함께 사용합니다. 전체 검정에 Holm 보정을 적용하며 RGB 히스토그램 JS는 참고값으로 보존합니다. [복합 판정과 표본 조건](drift-detection.md)을 참고하세요. 소스/도메인 차이이며 시간 경과나 모델 성능 저하를 확정하지 않습니다. GS SHOP과 무신사의 레이블 생성 방식 차이도 속성 결과에 영향을 줍니다.

## 수동 레이블 검토

워크스페이스에서 이미지를 누르면 해당 이미지의 레이블 편집 화면이 열립니다.
왼쪽 이미지는 확대할 수 있고, 오른쪽에서 선택한 기준과 상품 카테고리에 맞는 속성을 선택합니다. 디자인 디테일은 복수 선택입니다.
판단할 수 없는 단일 속성은 `unknown`(판단 어려움), 적용되지 않는 속성은
허용된 경우 `not_applicable`(해당 없음)을 사용합니다. 제외한 속성은 학습 손실과 평가에서 빠집니다.

`수정본 저장`은 해당 이미지의 레이블을 바꾼 전체 데이터셋을 새 불변 버전으로 저장합니다.
원본 데이터, 다른 이미지, train/validation/test 분할, 기존 학습·평가 기록은 유지됩니다.
화면은 저장된 버전으로 전환되며 이후 학습/평가에서도 이 버전을 선택할 수 있습니다.
저장할 때마다 버전이 하나 생성됩니다. 현재 페이지의 이전·다음 이미지 이동을 지원합니다.

사람 검토 완료는 사용자가 `전체 속성을 직접 검토했습니다`를 선택했을 때만 기록합니다.
속성이나 제외 설정을 다시 바꾸면 확인 체크를 해제합니다. 저장하지 않은 변경은 닫기/이동 전에
버릴지 확인하며, 저장 실패 시 입력을 유지합니다. 원래 AI 레이블 출처와 이전 값·메모·수정 시간을
새 버전 안에 남깁니다. 로그인 없는 서비스이므로 검토자의 개인 신원은 인증하거나 기록하지 않습니다.

API: `GET /api/label-schema`, `POST /api/datasets/{dataset_id}/samples/{sample_id}/labels`.
POST에는 해당 기준의 키를 모두 가진 `target`, `unscored_fields`, `human_verified`, `note`를 보냅니다.
성공하면 새 버전의 메타데이터와 수정한 샘플을 반환합니다. 허용되지 않은 속성/값은 422,
없는 데이터셋/샘플은 404입니다. 기존 샘플을 덮어쓰는 PATCH가 아닙니다.

## 비케이브 엑셀 기준

현재 기준은 `bkave-106baf22f720`입니다. 첨부된 `비케이브_Taxonomy_공유.xlsx`의
SHA256은 `106baf22f720`로 시작하며 전체 해시는 `backend/schemas/bkave_taxonomy.json`에 있습니다.
`python scripts/extract_taxonomy.py INPUT.xlsx OUTPUT.json`으로 엑셀 세 시트를 읽습니다.
원문 카테고리 64개, 색상 코드 212개, 카테고리별 속성·공통 속성의 철자를 그대로 보존합니다.
색상군의 옐로/옐로우, 같은 이름에 여러 코드가 있는 경우도 임의로 합치지 않습니다.
카테고리 코드 표는 기준 사전으로 보존하며 새로운 상품 분류 작업을 추가하지는 않습니다.

해당 범위의 허용값을 제공합니다. 데이터셋/학습 모델의 `schema_id`를 기준으로 UI·검증·프롬프트·평가가
같은 규칙을 사용합니다. 이전 데이터/모델은 `visual-v1`로 취급하고 계속 조회·편집·실행할 수 있습니다.
서로 다른 기준의 데이터 재구성·드리프트 비교·LoRA 모델 사용은 거절합니다. 기본 모델은 어느 기준에도
사용할 수 있습니다. 새 모델은 기준 ID, 프롬프트와 원문 사전 스냅샷을 보관합니다.

비케이브 속성 키는 `fit,length,sleeve,neckline,pattern,details,fabric,origin,color_code`입니다.
상품 카테고리는 기존 메타데이터의 아우터/상의/하의/ACC를 입력 문맥으로 사용합니다.
카테고리에 없는 속성은 시스템 값 `not_applicable`, 판단할 수 없는 값은 `unknown`으로 표시합니다.
이 둘은 비케이브가 정의한 추가 속성값이 아닙니다. UI에서는 해당 없음/판단 어려움으로 표시합니다.

`PYTHONPATH=. .venv/bin/python -m backend.migrate_taxonomy`는 이전 버전을 보존한 채
보수적 변환본을 생성합니다. 원본 버전·해시·기준·변환 정책으로 중복 생성을 방지합니다.
카테고리와 맞는 확실한 동의어만 변환하고, 이전의 작은 로고 무시 정책 때문에 확정할 수 없는
무늬는 미확인으로 둡니다. 이전 디테일은 새 전체 어휘를 검토한 결과가 아니므로 보이는 대응값을
검토용으로 보존하되 전체 필드를 학습/평가에서 제외합니다. 원단은 데님/니트/플리스처럼 근거 있는
기존 시각 레이블만 대응합니다. 생산처·세부 색상 코드는 원본 정답이 없으므로 미확인으로 두며
학습 손실과 평가에서 제외합니다. 사람 검토 완료로 자동 변경하지 않습니다.

`PYTHONPATH=. .venv/bin/python scripts/run_bkave_experiment.py`는 최초에 혼합 학습 버전을 만들고
2B/4B 각 100스텝과 동일 seed의 검증 32개 평가를 요청합니다. 실행 상태는 `.runtime/bkave-experiment.json`에
보관합니다. 기존 리포트가 있으면 그 작업을 이어 확인하며 임의로 새 실험을 중복 생성하지 않습니다.
작업 자체는 systemd 워커 큐에 영속 저장됩니다. 조정 스크립트가 중단되면 같은 명령으로 결과 확인과
평가 등록을 이어갈 수 있습니다. 기존 실행 리포트를 덮어쓰지 않고 새 실험을 하려면 별도 리포트를 지정하는
방식으로 스크립트를 확장해야 합니다. 학습 중에는 API/웹만 재시작하고 워커를 재시작하지 마세요.

`/api/label-schema`의 기본 응답은 비케이브 기준입니다. 기존 14개 속성 사전이 필요한 클라이언트는
`schema_id=visual-v1`을 명시해야 합니다. 비케이브 카테고리별 값은 `category=상의`처럼 함께 지정하세요.

## 목록 조회 인덱스와 갱신

API 초기화 시 `dataset_summaries`와 `dataset_images` 파생 테이블을 생성하고 기존 데이터를 채웁니다. 원본 `objects.body`는 유지합니다. SQLite 트리거가 데이터셋의 등록·수정·삭제와 같은 트랜잭션에서 파생 테이블을 갱신하므로, 별도 워커나 직접 SQL 쓰기도 반영되고 롤백 시 함께 복구됩니다. 최초 적용 전에는 기존 운영 절차에 따라 SQLite 온라인 백업을 보관하세요.

`GET /api/jobs?summary=true`는 결과와 전체 손실 이력을 제외한 목록을, `GET /api/models?summary=true`는 모델 목록에 필요한 메타데이터를 제공합니다. 파라미터가 없는 기존 API와 `/api/jobs/{id}`, `/api/models/{id}`는 전체 응답을 유지합니다. UI는 필요한 화면에서만 해당 작업 상세·학습 로그를 추가 조회합니다.

브라우저 확인은 `npm run test:loading`으로 실행하며 `TEST_BASE_URL`로 대상 주소를 지정할 수 있습니다. 초기 표시 측정값은 `.runtime/loading-after.json`에 기록됩니다. 이 검사는 기존 데이터와 완료된 평가/드리프트/학습 이력이 있는 운영 검증 환경을 대상으로 하며 작업을 새로 제출하지 않습니다.

### 워크스페이스 현재 데이터

`workspace_data(workspace_id, dataset_id)`가 화면에서 사용하는 이미지 목록을 가리킵니다. 초기 적용은 각 워크스페이스의 가장 최근 데이터를 지정하고 기존 객체 본문은 보존합니다. 데이터 전체 삭제 시 포인터를 NULL로 유지하여 과거 내부 데이터가 화면에 다시 나타나지 않도록 합니다. 이 테이블도 SQLite 전체 백업에 포함되며, 복원 시 임의로 삭제하거나 최신 시각만으로 다시 계산하지 않습니다.

모델 API는 [모델 API 운영](model-api.md)을 참조합니다. 외부 요청은 기존 웹 주소로 받으며, 영속 작업 큐를 공유합니다. 학습·평가는 GPU 0의 Transformers+PEFT, API 추론은 GPU 1의 vLLM에서 실행합니다.

### 재구성 결과 저장

재구성 입력은 원본의 **학습 및 미지정 데이터**다. 운영에서 유입된 이미지는 `unassigned`(미지정)로
보관할 수 있으며 화면 업로드의 기본값도 미지정이다. 학습/검증/테스트 용도를 미리 정하지 않아도
재구성 후보로 사용할 수 있다. 선택한 결과를 새 워크스페이스에 저장할 때만 `train`으로 배정하며
미지정에서 온 결과에는 `source_split=unassigned`를 남긴다. 원본의 레이블과 분할은 수정하지 않는다.
검증·테스트로 지정한 이미지는 후보와 결과에서 제외하고 원본에서 별도 평가에 사용한다.
속성 분포를 사용하는 선별에는 레이블이 필요하다. 미레이블 운영 데이터는 먼저 레이블링하거나,
레이블 없이도 가능한 전체 합치기로 모은 뒤 레이블링한다.
`데이터 수`는 결과 개수와 같고, 이미지 해시가 같은 데이터는 중복 제외한다.
미리보기는 저장하지 않으며 새 워크스페이스와 결과는 하나의 트랜잭션으로 저장한다.

화면의 기본 선별 방식은 균형 혼합(`balanced_mix`)이다. 선택한 원본마다 혼합 비율을 지정하며
처음에는 같은 비율로 설정한다. 비율을 바꾸면 나머지 원본의 비율도 합계 100%가 되도록 조정한다.
처음 제안하는 데이터 수는 원본별 수량으로 같은 비율을 채울 수 있는 범위에서 최대 200개로 정한다.
원본 데이터셋 ID별 목표 개수를 먼저 정하므로 같은 출처의 과거·신규 원본도 별도로 섞을 수 있다.
원본의 생성일을 과거·신규 판정에 사용하지 않는다. 시점별 비중을 따로 조절하려면 원본을 별도
워크스페이스로 선택한다. 각 원본의 카테고리·속성 주변 분포를 고려해 선별하고, 미확인·제외 값은
목표 레이블로 사용하지 않는다. 같은 시드의 비율 제약을 지킨 무작위 표본보다 원본별 분포 차이가
커지면 그 무작위 표본을 사용한다. 속성 간 결합 분포나 실제 학습 성능의 최적화를 보장하지 않는다.

`dataset_weights`는 선택한 데이터셋 ID별 0~100의 상대 비중을 받는다. 생략하면 동일 비중이다.
개수는 최대 나머지 방식으로 정수 배분하고, 공유 이미지는 한 원본에만 배정해 중복 없이 목표 개수를
유지한다. 중복 공유 관계까지 고려했을 때 비율을 채울 데이터가 부족하면 개수·비율 조정을 요구한다.
미리보기의 `selection.mix`는 목표·실제 비율과 개수를, `before_js`/`after_js`는 혼합 목표 속성 분포와의
차이를 제공한다. 별도 검증·테스트 데이터로 기존·신규 성능을 각각 확인해야 한다.

전체 합치기(`merge`), 무작위(`random`), 출처 균형(`source_balanced`),
기준 분포 맞추기(`distribution`)도 선택할 수 있다. 전체 합치기는 선택한 원본의 학습 및 미지정 후보를 모두 포함한다.
나머지는 `data_count`와 `seed`를 받는다. 분포 선별은 선택한 원본 중 `reference_id`를 지정하고
카테고리 및 속성값의 주변 분포에서 부족한 값을 우선 보충한다. 제외·미확인 속성은 기준 분포에 사용하지 않는다.
후보가 많은 경우 제한된 후보 탐색을 사용하므로 전역 최적화를 보장하지 않는다. 같은 시드의 무작위
표본보다 분포 차이가 커지면 무작위 표본으로 대체한다. 미리보기의 평균 JS 값으로 실제 차이를 확인한다.
기준의 값이 원본에 부족하거나 개수가 작으면 기준 분포와 정확히 같아지지는 않는다.

기존 API의 `train_budget`만 사용하는 무작위·출처 균형 호출은 검증·테스트를 함께 보존하던
동작을 유지한다. 새 화면은 `data_count`를 사용한다. 두 개수 필드를 함께 지정하면 거절한다.
새 API 요청과 화면의 기본값은 `balanced_mix`이다. 단, `train_budget`만 지정한 기존 요청에서
`method`를 생략한 경우는 호환성을 위해 출처 균형과 검증·테스트 보존 동작을 유지한다.
`workspace_id`를 생략하면 새 워크스페이스를 만들고, 명시하면 지정한 워크스페이스에 저장한다.

### 워크스페이스 레이블 모델

생성·수정 화면의 레이블 모델은 워크스페이스 `labeling_model_id`에 저장한다.
목록과 상세 화면, 자동 레이블링 창은 같은 설정을 사용한다. 설정이 없으면
자동 레이블링 창에서 임의의 모델을 선택하지 않는다. 기존 워크스페이스에
이 필드가 없으면 현재 데이터셋의 레이블링 모델 기록을 표시하며, 명시적으로
미설정(null)을 저장하면 과거 기록으로 대체하지 않는다. 과거 레이블 출처는
데이터셋에 보존한다. 자동 레이블링 전체 결과가 현재 워크스페이스에 반영된 성공 시점에 사용 모델을
워크스페이스에도 저장한다. 접수·실패·취소·부분 반영 시에는 기존 설정을 유지한다. 보관되거나 파일이 없는 모델은 새 실행에 사용할 수 없다.

### 레이블 상세 탐색과 검토

상세 화면은 열 때의 검색·필터 결과 전체 ID 목록을 기준으로 이전/다음 이미지를
이동한다. 목록의 24개 페이지 경계에 제한되지 않으며, 상세 데이터는 이동할 때
한 건씩 읽는다. 검토 상태 필터로 연 이미지를 저장해도 열린 상세의 탐색 순서는
유지된다. 저장 성공 시 `human_verified=true`로 기록하며 별도 확인 체크박스는 없다.
기준명·내부 상품 ID·판독 원문은 상세 화면에 표시하지 않지만 저장 데이터는 유지한다.

### 이미지 데이터 구분과 일괄 작업

레이블 상세의 `데이터 구분`에서 학습·검증·테스트를 선택하고 저장한다.
저장은 레이블과 데이터 구분을 함께 반영하며 검토 완료로 처리한다.
목록의 이미지 체크박스로 여러 장을 선택하고 `선택 이동` 또는 `선택 삭제`를 실행한다.
페이지를 넘겨도 선택을 유지하며, 검색·필터·현재 데이터가 바뀌면 선택을 해제한다.
`현재 페이지 전체 선택`은 현재 페이지에만 적용된다. 삭제는 기존 삭제 목록에서 복원할 수 있다.

일괄 이동 API는 `POST /api/datasets/{did}/samples/split`이며
`sample_ids`와 `split`(`train`, `validation`, `test`)을 받는다.
레이블과 검토 상태를 유지하고 새 데이터 버전을 생성하므로 기존 작업 입력은 바뀌지 않는다.
선택 항목이 없거나 유효하지 않으면 전체 요청을 거절하며, 현재 버전이 바뀌면 409를 반환한다.
데이터 구분 변경은 각 이미지의 `split_history`에 보존하고 레이블 수정 이력에는 섞지 않는다.
진행 중인 자동 레이블링 결과를 반영할 때도 사용자가 변경한 데이터 구분을 유지한다.

### 목록과 결과 페이지

모델 목록, 실행 이력, 이미지별 평가 결과는 10개씩 표시한다. 이전/다음과 페이지 번호로
이동하며 모델 검색·유형 변경 및 평가 실행 선택 시 해당 결과는 첫 페이지부터 표시한다.
API 요청 이력은 `paginated=true&offset=...&limit=10`으로 조회하므로 최근 20건보다
오래된 요청도 확인할 수 있다. 요청 결과의 진행 상태는 목록 페이지와 별도로 갱신한다.
이미지 목록은 기존 24개 단위를 유지하며 선택한 항목은 페이지를 넘겨도 유지된다.

학습 설정 창의 `적용`은 설정만 반영한다. Enter도 같은 동작이며 학습은 화면의
`학습 시작`으로 실행한다. 취소·Esc로 닫은 입력은 반영하지 않는다.
레이블 상세는 이미지 탐색 목록을 조회하는 동안에도 닫을 수 있다.
모델 상세의 학습 데이터 이름과 평가 결과 이미지는 당시 데이터 버전에서 조회한다.
모델 목록의 `q`, `type`, `page` 주소 매개변수는 상세 이동·복귀·새로고침 시 유지한다.
API 이력은 조회 성공 시 페이지 번호와 행을 함께 반영하며, 실패하면 기존 목록과
번호를 유지하고 같은 위치에서 재시도할 수 있다.
